# 平台后续开发建议

先保持基本测试链路稳定，再开发平台能力，不以补齐 HireFlow 的所有业务场景为前置条件。

## 已完成的基础能力

- URL 直接运行与可选多项目 JSON 配置：项目名、URL、适配器、all/smoke 范围，严格校验且不保存凭据或写入授权。
- 每次独立的运行目录、版本化摘要与原生 HTML/JSON/JUnit 报告；保留失败、跳过、flaky、未执行和运行器错误信息。
- 平台自身单元/集成检查接入 push/PR CI，不访问真实业务应用。

## 第一优先级

1. 在现有配置基础上补充确有需求的用例标签、账号角色声明；凭据继续通过私有环境注入。
2. 用例分层：明确 smoke / regression / isolated-write，支持按模块、角色、标签执行。
3. 在现有结果摘要上完善可复现筛选与失败归因；不能仅凭失败状态判断业务缺陷或基础设施故障。
4. 认证适配：受限测试账号、环境隔离、报告脱敏，不保存真实密码或浏览器会话进仓库。
5. 接入第二个项目验证复用程度，避免过早围绕 HireFlow 定制出一套平台。

## 下一阶段

- 对受信任外部资源提供显式 allowlist，完善 HTTP 跳转、SSO 和 WebSocket 场景。
- 增加稳定性/重复运行检查，失败归因与历史趋势。
- 按实际需求接入现有 CI、Allure 等成熟报告组件，评估后再决定是否需要独立 Web 控制台。

## 暂不优先

自建浏览器调度器、自研测试执行引擎、无边界 AI 自主点击、在生产上自动生成/删除业务数据，以及追求单项目全功能覆盖。
